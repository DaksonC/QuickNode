Project structure

A QuickNode project splits src/ into two layers: domain holds the business rules (entities, repository interfaces, use cases) and infrastructure holds everything that talks to the outside world (HTTP, database, logs, docs).

C:\> What is in each folder?

src/
├── domain/                  business rules, no Express or ORM
│   ├── entities/            User and its input types
│   ├── repositories/        UserRepository interface
│   └── use-cases/           CreateUser, GetUser, UpdateUser...
├── infrastructure/          adapters to the outside world
│   ├── config/              load-env: reads .env with Node's loader
│   ├── controllers/         HTTP in, use case call, HTTP out
│   ├── database/
│   │   ├── connection.ts    TypeORM data source
│   │   ├── entities/        TypeORM table mappings
│   │   ├── repositories/    UserRepository implementation
│   │   └── repository-factory.ts
│   ├── docs/                Swagger (OpenAPI 3) setup
│   ├── logging/             pino logger
│   ├── middleware/          validation and error handler
│   └── routes/              Express routers
├── __tests__/               Jest tests of the use cases
└── server.ts                wiring: repository → use cases → controller → routes

The JavaScript template has the same layers, with Sequelize models in infrastructure/database/models/ instead of TypeORM entities.

C:\> What is the dependency rule?

Dependencies point inwards: infrastructure may import domain, but domain never imports infrastructure, Express or the ORM. A use case receives a repository interface in its constructor; server.ts decides which implementation it gets.

HTTP request
  → routes/        (Express router, request validation)
  → controllers/   (turns HTTP into a call)
  → use-cases/     (business rule)          ← domain
  → repositories/  (interface)              ← domain
  ← database/repositories/ (TypeORM implementation)

Keeping this rule is what lets you test use cases without a database and replace Express or the ORM later. A qn check command that enforces it automatically is planned.

C:\> What does each layer do?

domain/entities
Plain classes with the data and behavior of the business (User.updateName()). In the TypeScript template they also carry the class-validator DTOs used to validate input.
domain/repositories
Interfaces that say what the domain needs from storage (findByEmail, create…), never how.
domain/use-cases
One class per action, with an execute() method. Rules such as "the email must be unique" live here.
infrastructure/database
The connection, the ORM mappings and the classes that implement the repository interfaces, converting rows into domain entities.
infrastructure/controllers and routes
Translate HTTP into use case calls and results into JSON responses, with status codes and Swagger annotations.
server.ts
The composition root: creates the repository, injects it into the use cases, the use cases into the controller and mounts the routes under /api/v1.

C:\> Which files sit at the project root?

  • .env: generated with random DB_PASSWORD and JWT_SECRET, git-ignored, permission 600. .env.example documents every variable.
  • docker-compose.yml: PostgreSQL 17 and Adminer, both bound to 127.0.0.1.
  • eslint.config.mjs, .prettierrc.json, jest.config.js, commitlint.config.js and .husky/: quality tools.

Scripts: npm run dev, npm test, npm run lint, npm run docker:up, npm run db:seed; the TypeScript template adds npm run build.
