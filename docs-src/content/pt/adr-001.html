ADR-001 — Evolução, segurança e leveza do QuickNode CLI

O ADR-001 decide que o QuickNode CLI não terá dependências de runtime, vai gerar projetos seguros por padrão, será publicado com procedência verificável e ganhará este site de documentação bilíngue, em fases da v1.2.0 à v3.

Status: Proposto · Pacote: @10565/quicknode-cli v1.1.1 · Escopo: CLI qn, templates gerados e documentação

Versão original. Há uma English translation.

C:\> 1. Contexto

O QuickNode CLI inicializa projetos Node.js com arquitetura limpa (camadas domain e infrastructure) e ferramentas já configuradas. Hoje oferece um único comando, qn create [nome] [-ts|-js], que copia um de dois templates:

  • TypeScript: Express, TypeORM, class-validator, Swagger, pino, helmet, Jest, ESLint/Prettier, Husky + commitlint, Postgres via docker-compose.
  • JavaScript: a mesma base com Sequelize no lugar do TypeORM.

A última versão (1.1.1) é de 28/09/2025. A visão do projeto vai além do scaffolding: ter comandos que configurem automaticamente ferramentas consolidadas no mercado. Antes de crescer em funcionalidades, a lib precisa de uma base segura e leve, que é o motivo deste ADR.

C:\> 3. Decisão

Adotar cinco princípios que valem para toda mudança futura e executar as decisões D1 a D9.

Princípios

  • Zero dependências de runtime. Qualquer exceção exige um ADR próprio com justificativa, tamanho e histórico de manutenção do pacote.
  • Seguro por padrão. Nada destrutivo, nenhum segredo fixo, nenhum script executado sem opt-in.
  • Não destrutivo e previsível. O mesmo comando com as mesmas entradas gera o mesmo resultado; --dry-run mostra o que vai acontecer.
  • Templates como dados vivos. Os templates são testados e auditados no CI como se fossem produtos.
  • Cadeia de suprimentos verificável. Toda versão publicada é rastreável até um commit e um build de CI.

D1 — Substituir todas as dependências por APIs nativas do Node

Exigir node >= 22 (LTS) e trocar:

HojeSubstituto nativo
commanderutil.parseArgs (node:util)
chalkutil.styleText, respeitando NO_COLOR e saída não-TTY
figletBanner ASCII estático já pré-renderizado (a função createSimpleBanner já existe)
fs-extrafs/promises: cp, mkdir, readFile, writeFile, rename
inquirerreadline/promises para texto, confirmação e escolha numerada
oraMensagens de etapa simples ou um spinner próprio de poucas linhas

Se no futuro for necessária uma UX mais rica (seleção com setas, multi-select), avaliar uma única dependência pequena e sem dependências transitivas, via ADR.

D2 — Proteções no comando create

  • Validar o nome com as regras de nome de pacote do npm (minúsculas, até 214 caracteres, sem /, \, .. ou caminho absoluto) e garantir que o diretório resolvido fique dentro do diretório atual.
  • Recusar diretório não vazio (ignorando .git), a menos que o usuário passe --force; com ., listar os arquivos em conflito antes de qualquer escrita.
  • Gerar o projeto em diretório temporário e mover no final, para não deixar projeto pela metade em caso de erro.
  • Copiar sem seguir symlinks e garantir no CI que os templates não contenham symlinks.
  • npm install e git init só com opt-in explícito (--install, --git), executados com spawn sem shell.

D3 — Templates seguros e enxutos

  • Remover os package-lock.json dos templates; o lock é criado no primeiro npm install do usuário com versões atuais.
  • Manter as versões dos templates atualizadas por Dependabot/Renovate e falhar o CI se o projeto gerado tiver vulnerabilidade alta ou crítica.
  • Gerar no .env local (ignorado pelo git) um JWT_SECRET e uma senha de banco aleatórios com crypto.randomBytes; o .env.example fica só com placeholders.
  • Publicar o Postgres em 127.0.0.1:5432 no docker-compose.
  • Atualizar ferramentas: ESLint 9 (flat config), Husky 9, engines: >=22; avaliar Express 5.
  • Reduzir devDependencies dos templates usando recursos nativos: node --watch no lugar de nodemon, node --env-file no lugar de dotenv; avaliar node:test e a remoção de tipos nativa do Node para TypeScript.
  • Remover arquivos órfãos (user-routes-new.js).

D4 — Pacote publicado enxuto

  • Templates em um único lugar, resolvidos a partir da raiz do pacote (sem copiar para dist).
  • Campo files sem testes compilados e sem .d.ts desnecessários; corrigir ou remover main; tirar o prepare do pacote publicado.
  • Orçamento de tamanho no CI: falhar se npm pack --dry-run passar de 300 KB descompactado.

D5 — Cadeia de suprimentos

  • Publicar apenas pelo GitHub Actions com Trusted Publishing (OIDC) e --provenance; 2FA obrigatório na conta e nenhum token de longa duração.
  • CI com npm ci, lint, testes, npm audit, npm audit signatures; actions fixadas por SHA; OpenSSF Scorecard.
  • SECURITY.md com canal de reporte e política de versões suportadas.

D6 — Evolução funcional

Regra geral: priorizar comandos que ajudam no dia a dia de quem já criou o projeto, em vez de multiplicar variações do create. Toda opção nova precisa caber na matriz de testes do CI (D5) e manter o princípio 1. Todos os comandos que escrevem arquivos aceitam --dry-run, não sobrescrevem sem --force e respeitam o modo CI (--yes, --json).

Comandos novos (prioridade alta)

  • qn generate <tipo> <nome> (atalho qn g): gera os arquivos de uma funcionalidade já nas camadas corretas. qn g crud product cria entidade, caso de uso, interface e implementação do repositório, controller, rota e teste, todos ligados. Tipos: crud, entity, usecase, repository, controller. Opções: --only <tipo>, --no-test, --dry-run. É o que faz a arquitetura limpa se manter no projeto depois do create.
  • qn check: valida a regra de dependência da arquitetura limpa. Lê os imports (sem dependências, só com fs e análise simples de import/require) e falha se, por exemplo, domain importar infrastructure, Express ou ORM. Saída legível e --json; código de saída diferente de zero para uso em CI e no pre-commit. É um diferencial da lib em relação a outros scaffolders.
  • Instruções para agentes de IA no projeto gerado: um AGENTS.md (com cópia em CLAUDE.md) descrevendo as camadas, a regra de dependência, como rodar testes, lint e qn check, e como usar qn generate. Assim, assistentes como Copilot e Claude Code respeitam a arquitetura. Também disponível em projetos existentes via qn add agents.
  • qn add <recurso>: aplica de forma idempotente uma ferramenta a um projeto existente, com --dry-run mostrando o diff. É a realização da visão de "comandos que configuram ferramentas". Receitas:
  • Já previstas: docker, eslint, husky (com commitlint), swagger, github-actions, tests.
  • Novas: auth (JWT com segredo vindo do .env), healthcheck (rotas de saúde e prontidão), ci (GitHub Actions com lint, testes, qn check e npm audit), docker em etapas rodando sem root, graceful-shutdown, rate-limit e agents.
  • qn doctor: verifica versão do Node, .env, Docker, vulnerabilidades do projeto e roda o qn check.

Comandos novos (segundo momento)

  • quicknode.json no projeto gerado: registra as escolhas do create (banco, gerenciador de pacotes, versão do template, pastas de cada camada). qn add, qn generate, qn check e qn upgrade leem esse arquivo para saber como o projeto está organizado. Permite presets: qn create --preset api-minima ou um preset local em JSON, validado antes do uso.
  • qn upgrade: aplica num projeto existente as melhorias de uma versão nova do template. Usa o quicknode.json e o hash dos arquivos gerados para separar o que o usuário alterou; arquivos não alterados são atualizados, arquivos alterados recebem um diff para revisão manual. Sempre com --dry-run e nunca sobrescreve sem confirmação. É o item mais complexo da lista.
  • qn env: compara .env com .env.example, lista variáveis faltando ou sobrando e gera segredos com crypto.randomBytes (qn env --generate-secrets). Nunca imprime os valores dos segredos.

Comportamento geral

  • Modo CI: --yes (sem prompts), --json na saída, sem banner quando não for TTY. Banner e link de doação só em --help ou na primeira execução.
  • Sem telemetria.
  • Fora do escopo: templates de front-end, suporte a muitos bancos e monorepos. Puxam dependências e transformam a lib em outro produto.

D7 — Documentação e interface de uso, com a identidade do site pessoal

O dev precisa de um lugar claro para aprender a usar a lib e o projeto gerado. Essa interface fica fora do pacote npm, para não ferir os princípios 1 e 2, e segue a mesma identidade visual e as mesmas regras técnicas do site pessoal profissional (daksonc.github.io), para que o projeto seja reconhecido como parte do mesmo portfólio.

Onde fica e como é construída

  • Site estático em docs/ no repositório do QuickNode, publicado pelo GitHub Pages. Como o site pessoal já é daksonc.github.io, a documentação fica naturalmente em daksonc.github.io/QuickNode/, no mesmo domínio.
  • Mesma arquitetura do site pessoal: HTML, CSS e JavaScript puros, sem framework, sem etapa de build obrigatória e sem recursos de terceiros (nada de CDN, Google Fonts ou analytics). Isso também cumpre o princípio 1 na documentação.
  • A referência de comandos é gerada por um script Node próprio, sem dependências, a partir da mesma definição usada pelo parseArgs, para a documentação nunca divergir da CLI. O HTML gerado é commitado.
  • Orçamento igual ao do site: cada página com menos de 100 KB (sem contar a fonte).

  • Visual de terminal DOS: prompt no cabeçalho (ex.: C:\QUICKNODE>), botões e seletores entre colchetes ([MENU], [EN], [PT]), títulos de seção com linha tracejada, listas com o marcador > e blocos de código como saída de terminal.
  • Acessibilidade WCAG 2.2 AA, como no site: contraste mínimo de 4,5:1 nos dois temas, foco visível com inversão verde/preto, lang correto e conteúdo legível a 320 px.
  • Efeitos CRT (brilho e scanlines) só por opt-in ([FX: ON]), apenas no tema escuro e desligados com prefers-reduced-motion.
  • Bilíngue EN/PT, com a mesma estrutura de páginas e seletor de idioma do site; tema claro/escuro salvo antes da primeira pintura, sem "flash".
  • Linha de comando opcional na página, como no site, simulando qn --help, qn create, qn add e qn ui para o dev experimentar antes de instalar. É melhoria progressiva: a página funciona inteira sem JavaScript.
  • Coerência no terminal: a própria CLI usa a mesma lógica de cores via util.styleText (verde para sucesso, âmbar para destaques e links) e o banner ASCII segue o mesmo estilo.
  • Os tokens são copiados para docs/assets/css/ com um comentário apontando a origem, em vez de importados do repositório do site, para que os dois projetos publiquem de forma independente.

Conteúdo mínimo

  • Primeiros passos; referência de cada comando e flag; estrutura do projeto gerado e o papel de cada camada da arquitetura limpa; como criar uma nova entidade e caso de uso; receitas do qn add; perguntas frequentes; os ADRs publicados.
  • Ajuda offline no terminal: qn help <comando> e qn <comando> --help, sempre com exemplos.
  • qn ui [tópico] (apelido: qn docs [tópico]): abre o navegador do usuário na página da documentação. Regras:
  • URL fixa: base https://daksonc.github.io/QuickNode/; o tópico só escolhe uma entrada de uma lista fechada (ex.: start, create, add). Nenhum texto digitado pelo usuário entra na URL, o que impede redirecionamento para outro site.
  • Abertura nativa, sem shell: spawn com argumentos em lista, usando o programa do sistema: open (macOS), explorer.exe (Windows; nunca cmd /c start, que interpreta &) e xdg-open (Linux). Processo detached e unref, para a CLI terminar na hora.
  • Link sempre impresso no terminal. Em CI, SSH, contêiner ou saída não interativa, o comando só imprime o link e não tenta abrir nada; a opção --print força esse comportamento.
  • Falha silenciosa: se não houver programa para abrir links, o link impresso basta e o comando termina com sucesso.
  • Zero dependências: nada de pacotes como open.
  • Projeto gerado com README contendo o mapa das pastas e links para o guia.

Fora do escopo: servidor web ou UI embutida na CLI. O qn ui apenas abre a documentação publicada; ele nunca sobe servidor local, abre porta ou adiciona dependências ao pacote. Uma UI local só seria reavaliada, via ADR próprio, se surgir demanda real (por exemplo, um assistente visual de criação de projeto).

D8 — SEO e descoberta da lib

Objetivo: fazer a lib ser encontrada por quem busca soluções de scaffolding e arquitetura limpa em Node.js, sem telemetria e sem recursos de terceiros.

No site de documentação

  • Metadados por página: <title> e meta description únicos, link rel="canonical" e hreflang EN/PT (com x-default), no mesmo padrão do site pessoal.
  • Compartilhamento: Open Graph e Twitter Card com imagem de prévia (1200×630) no visual de terminal da D7.
  • Dados estruturados (JSON-LD): SoftwareApplication na página inicial (nome, descrição, licença, link do npm e do repositório) e BreadcrumbList nas páginas internas.
  • Sitemap e robots: sitemap.xml próprio em daksonc.github.io/QuickNode/sitemap.xml. Como o robots.txt só vale na raiz do domínio, que pertence ao repositório do site pessoal, o sitemap do QuickNode é referenciado no robots.txt do site pessoal. Verificação do domínio daksonc.github.io no Google Search Console cobre os dois.
  • Conteúdo orientado a busca: páginas e tutoriais, em EN e PT, para intenções como "Node.js clean architecture boilerplate", "Express + TypeScript com arquitetura limpa", "como criar um caso de uso" e "como validar a regra de dependência"; changelog público por versão.
  • Rastreabilidade: todo o conteúdo está no HTML; o simulador de terminal e os efeitos são só melhoria progressiva. URLs limpas e estáveis por tópico (as mesmas usadas pelo qn ui).
  • Desempenho: limite de 100 KB por página, preload da fonte e font-display: swap; meta de Lighthouse > 95 em SEO, desempenho e acessibilidade.
  • Opcional: llms.txt com o resumo da documentação, para buscadores e assistentes com IA.

SEO para buscadores com IA

Além dos buscadores tradicionais, a documentação deve ser fácil de ler, entender e citar por buscadores e assistentes com IA (ChatGPT, Claude, Perplexity, respostas com IA do Google). Complementa o llms.txt, as páginas em .md e o posicionamento definidos na D9.

  • Robôs de IA no robots.txt: permitir explicitamente os rastreadores de IA (ex.: GPTBot, ClaudeBot, PerplexityBot e Google-Extended) para que a documentação possa ser lida e citada. Como o robots.txt fica na raiz do domínio, no repositório do site pessoal, a regra vale para os dois sites e é registrada também lá.
  • Conteúdo em formato de resposta: cada página começa com uma frase que responde diretamente à pergunta principal (ex.: "Para criar uma API Node.js com arquitetura limpa, rode npx @10565/quicknode-cli create minha-api"), usa títulos em forma de pergunta e passos numerados, para facilitar a extração de trechos.
  • Datas e versões visíveis: cada página mostra "atualizado em" e a versão a que se aplica (ex.: "válido para a v2.x"), também no JSON-LD (dateModified, softwareVersion), para sinalizar que a fonte está atual.
  • Fatos consistentes em todos os canais: nome, comando de instalação, versão atual e frase de posicionamento idênticos no npm, no GitHub, na documentação e em artigos externos. Informação contraditória entre fontes leva modelos a errar ou deixar de recomendar a lib.
  • Página de comparação honesta: quando usar o QuickNode, o Nest CLI ou um template manual, com critérios objetivos, já que perguntas comparativas são frequentes em assistentes de IA.
  • Limite conhecido: a otimização para buscadores com IA ainda é recente e muda rápido; esses itens aumentam a chance de citação, mas não a garantem, e não há ferramenta equivalente ao Search Console para medi-la. O acompanhamento é feito com consultas periódicas a assistentes de IA (ex.: "como criar uma API Node.js com arquitetura limpa"), registrando se a lib aparece e se os dados citados estão corretos.

No npm e no GitHub

  • package.json: description objetiva; keywords ampliadas (scaffold, generator, boilerplate, clean-architecture, express, typescript-template, nodejs); homepage apontando para a documentação; repository e bugs corretos.
  • Sinais de qualidade do npm: provenance, testes, releases frequentes e zero dependências (D1 a D5) também melhoram a posição na busca do npm.
  • GitHub: descrição e topics no repositório, campo "Website" com o link da documentação, imagem de prévia social, releases com notas e README que abre com um GIF do qn create e o comando de instalação.
  • npm create quicknode: o apelido create-quicknode (seção 4) também é um canal de descoberta.
  • Crédito nos projetos gerados: uma linha "Gerado com QuickNode" com link no README do projeto, removível com --no-credits. Nunca em código, cabeçalhos HTTP ou respostas da API.

Fora do código

  • Divulgação técnica: artigo do TCC (quando publicado) citando a lib como referência acadêmica; artigos no dev.to e no LinkedIn mostrando qn check e qn generate.

Fora do escopo: analytics, pixels de rastreamento ou qualquer coleta de dados de visitantes, coerente com a regra de "sem telemetria" e "sem recursos de terceiros".

D9 — Experiência para agentes de IA

LLMs e agentes de código (Claude Code, Copilot, Cursor e similares) passam a sugerir, instalar e operar a lib no lugar do dev. A experiência do agente é tratada como experiência de usuário de primeira classe: o agente precisa descobrir o que a lib faz, executá-la sem travar, entender erros e produzir código que respeite a arquitetura, sempre com a pessoa no controle das ações que alteram arquivos.

CLI operável por agentes

  • Nunca bloquear: todo prompt interativo tem uma flag equivalente. Sem TTY (agente, CI, pipe), o qn nunca pergunta: usa os padrões declarados ou falha imediatamente informando qual flag falta.
  • Autodescrição: qn schema (e qn --help --json) devolve a especificação completa de comandos, flags, valores aceitos e padrões em JSON, gerada da mesma definição usada pelo parseArgs e pela documentação (D7). O agente descobre o que existe em vez de inventar flags.
  • Erros acionáveis: todo erro tem código estável, mensagem curta e sugestão de correção, inclusive em --json (ex.: {"code":"E_DIR_NOT_EMPTY","message":"…","fix":"qn create minha-api --force"}). Os códigos e os códigos de saída ficam documentados.
  • Plano antes de agir: --dry-run --json devolve a lista de arquivos a criar, alterar ou remover, para o agente mostrar à pessoa antes de aplicar.
  • Saída estável: o formato JSON é versionado; mudanças incompatíveis só em versão major.

Servidor MCP

  • Expor create, generate, add, check, doctor e schema como ferramentas MCP (Model Context Protocol), para assistentes chamarem a lib de forma estruturada em vez de montar comandos de shell.
  • Distribuído como pacote separado (@10565/quicknode-mcp) ou implementado com JSON-RPC mínimo sobre stdio, sem SDK, para manter o princípio 1 no pacote principal.
  • Segurança: atua apenas dentro do diretório do projeto; sem acesso à rede; dry-run como padrão; escrita só com parâmetro explícito de confirmação; nunca executa comandos arbitrários.

Documentação legível por LLMs

  • llms.txt (índice) e llms-full.txt (conteúdo completo) na raiz da documentação; cada página também disponível em Markdown na mesma URL com .md.
  • Página "Para agentes de IA" com comandos exatos, não interativos e com versão fixada (ex.: npx @10565/quicknode-cli@2 create minha-api --typescript --db postgres --yes), fluxo recomendado e códigos de erro.
  • Página "Quando usar e quando não usar", com critérios claros, para que modelos recomendem a lib só nos contextos certos.
  • Posicionamento único repetido no npm, no README, no GitHub e na documentação: "CLI sem dependências para criar APIs Node.js com arquitetura limpa".

Proteção contra alucinação e confusão de nome

  • "QuickNode" também é o nome de um provedor de infraestrutura blockchain. README e documentação trazem um aviso explícito ("não confundir com…") e o nome completo do pacote com escopo em todos os exemplos.
  • Reservar nomes próximos no npm (create-quicknode e variações sem escopo) para evitar typosquatting de pacotes que LLMs possam sugerir por engano.
  • Instalação segura mesmo sem revisão humana: nenhum script de ciclo de vida (preinstall, postinstall), nenhum download durante a geração e provenance para verificar a origem (D5).
  • Templates e documentação nunca contêm instruções direcionadas a agentes fora do escopo do projeto, para não abrir espaço para prompt injection.

Projeto gerado pronto para IA

  • O AGENTS.md (D6) orienta o agente a preferir qn generate a escrever estrutura à mão, a rodar qn check e os testes após cada mudança e a registrar decisões em docs/adr/.
  • qn check e testes funcionam como trilhos: feedback imediato e determinístico para o agente corrigir o próprio código.
  • Pasta docs/adr/ com um modelo de ADR no projeto gerado, para que decisões de arquitetura fiquem registradas e sejam respeitadas por pessoas e agentes.

Avaliação contínua com agentes

  • Bateria de tarefas reais executadas periodicamente por agentes (ex.: "crie uma API com Postgres e um CRUD de produto", "adicione autenticação JWT"), medindo taxa de sucesso sem intervenção humana, flags inventadas e violações apontadas pelo qn check.

Fora do escopo: chamar LLMs a partir da CLI, embutir chaves de API ou enviar código do usuário para serviços externos. A lib se torna fácil de usar por agentes, mas continua offline e sem telemetria.

C:\> 5. Consequências

Positivas

  • Instalação via npx quase instantânea, com um único pacote.
  • Projetos gerados sem vulnerabilidades conhecidas e sem segredos fixos.
  • Nenhum risco de apagar arquivos do usuário.
  • Publicações verificáveis e documentação com a mesma identidade do site pessoal, o que aumenta a confiança para adoção e fortalece o portfólio.

Negativas e riscos

  • Exigir Node 22+ é uma quebra de compatibilidade: a mudança sai como v2.0.0 (semver major), com nota de migração.
  • Prompts nativos são menos sofisticados que os do inquirer.
  • Manter templates atualizados passa a ser trabalho contínuo, mitigado por automação (Dependabot + CI que gera e testa os projetos).
  • O formato JSON e os códigos de erro viram contrato público: mudá-los quebra agentes e integrações, então exigem versionamento cuidadoso.
  • Tokens visuais copiados podem divergir do site pessoal com o tempo; mitigar com uma verificação no CI que compara as variáveis CSS dos dois repositórios.
