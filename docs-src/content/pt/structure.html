Estrutura do projeto

Um projeto QuickNode divide o src/ em duas camadas: domain guarda as regras de negócio (entidades, interfaces de repositório, casos de uso) e infrastructure guarda tudo o que fala com o mundo externo (HTTP, banco, logs, documentação).

C:\> O que tem em cada pasta?

src/
├── domain/                  regras de negócio, sem Express nem ORM
│   ├── entities/            User e seus tipos de entrada
│   ├── repositories/        interface UserRepository
│   └── use-cases/           CreateUser, GetUser, UpdateUser...
├── infrastructure/          adaptadores para o mundo externo
│   ├── config/              load-env: lê o .env com o loader do Node
│   ├── controllers/         entra HTTP, chama o caso de uso, sai HTTP
│   ├── database/
│   │   ├── connection.ts    data source do TypeORM
│   │   ├── entities/        mapeamento das tabelas no TypeORM
│   │   ├── repositories/    implementação do UserRepository
│   │   └── repository-factory.ts
│   ├── docs/                configuração do Swagger (OpenAPI 3)
│   ├── logging/             logger pino
│   ├── middleware/          validação e tratamento de erros
│   └── routes/              routers do Express
├── __tests__/               testes Jest dos casos de uso
└── server.ts                montagem: repositório → casos de uso → controller → rotas

O template JavaScript tem as mesmas camadas, com models do Sequelize em infrastructure/database/models/ no lugar das entidades do TypeORM.

C:\> Qual é a regra de dependência?

As dependências apontam para dentro: infrastructure pode importar domain, mas domain nunca importa infrastructure, Express ou o ORM. Um caso de uso recebe uma interface de repositório no construtor; quem decide a implementação é o server.ts.

requisição HTTP
  → routes/        (router do Express, validação)
  → controllers/   (transforma HTTP numa chamada)
  → use-cases/     (regra de negócio)        ← domínio
  → repositories/  (interface)               ← domínio
  ← database/repositories/ (implementação TypeORM)

Manter essa regra é o que permite testar casos de uso sem banco e trocar o Express ou o ORM depois. Um comando qn check, que vai verificar a regra automaticamente, está planejado.

C:\> O que cada camada faz?

domain/entities
Classes simples com os dados e o comportamento do negócio (User.updateName()). No template TypeScript elas também trazem os DTOs do class-validator que validam a entrada.
domain/repositories
Interfaces que dizem do que o domínio precisa do armazenamento (findByEmail, create…), nunca como.
domain/use-cases
Uma classe por ação, com um método execute(). Regras como "o e-mail precisa ser único" ficam aqui.
infrastructure/database
A conexão, o mapeamento do ORM e as classes que implementam as interfaces de repositório, convertendo linhas em entidades do domínio.
infrastructure/controllers e routes
Traduzem HTTP em chamadas aos casos de uso e os resultados em respostas JSON, com status e anotações do Swagger.
server.ts
A raiz de composição: cria o repositório, injeta nos casos de uso, os casos de uso no controller e monta as rotas em /api/v1.

C:\> Quais arquivos ficam na raiz?

  • .env: gerado com DB_PASSWORD e JWT_SECRET aleatórios, ignorado pelo git, permissão 600. O .env.example documenta cada variável.
  • docker-compose.yml: PostgreSQL 17 e Adminer, ambos presos a 127.0.0.1.
  • eslint.config.mjs, .prettierrc.json, jest.config.js, commitlint.config.js e .husky/: ferramentas de qualidade.

Scripts: npm run dev, npm test, npm run lint, npm run docker:up, npm run db:seed; o template TypeScript tem também npm run build.
