# ADR-001 — Evolution, security and lightness of QuickNode CLI

ADR-001 decides that QuickNode CLI has zero runtime dependencies, generates projects that are safe by default, is published with verifiable provenance and gets this bilingual documentation site, in phases from v1.2.0 to v3.

Status: Proposed · Package: @10565/quicknode-cli v1.1.1 · Scope: the qn CLI, generated templates and documentation

Faithful translation of the Portuguese original, [ADR-001 em português](https://daksonc.github.io/QuickNode/pt/adr/001/).

## 1. Context

QuickNode CLI bootstraps Node.js projects with clean architecture (domain and infrastructure layers) and tools already configured. Today it offers a single command, qn create [name] [-ts|-js], which copies one of two templates:

- TypeScript: Express, TypeORM, class-validator, Swagger, pino, helmet, Jest, ESLint/Prettier, Husky + commitlint, Postgres through docker-compose.
- JavaScript: the same base with Sequelize instead of TypeORM.

The latest version (1.1.1) is from 2025-09-28. The project's vision goes beyond scaffolding: to have commands that automatically configure tools that are well established in the market. Before growing in features, the library needs a secure and light base, which is the reason for this ADR.

## 2. Diagnosis (verified on 2026-11-13)

The published package was downloaded, installed with --ignore-scripts, run and audited.

| Area | Finding | Impact |
| --- | --- | --- |
| Runtime dependencies | 6 direct ones (chalk, commander, figlet, fs-extra, inquirer, ora) pull 56 packages and 39 MB into node_modules. figlet alone takes 22 MB and rxjs (through inquirer) 12 MB. | Slow, heavy npx and a large supply chain surface to draw a banner and ask two questions. |
| Package size | 139 files, 1.6 MB unpacked. Templates are duplicated (/templates and /dist/templates, 1.1 MB each). Compiled tests ship in dist/__tests__. | Needlessly heavy download and install. |
| Generated projects | Templates ship frozen package-lock.json files (287 KB and 430 KB). npm audit on them: TS = 45 vulnerabilities (3 critical, 25 high); JS = 31 (1 critical, 14 high). | Every new project is born vulnerable. This is the most serious risk today. |
| Silent overwrite | qn create demo on an existing folder overwrote the user's README.md without warning (tested). With . the template is copied over the current directory. | User data loss. |
| Name validation | qn create ../escaped created the project outside the current directory (tested). The name is not validated and goes straight into package.json. | Path traversal and an invalid package.json. |
| Default secrets | docker-compose.yml and .env.example use password and your-super-secure-jwt-secret-key; Postgres is published on 5432 on every interface. | Weak credentials that tend to reach real environments. |
| Publishing supply chain | No provenance (only the registry's default signature), no SBOM, a prepare: husky install script in the published package. | There is no way to prove the tarball came from the repository. |
| Maintenance | main points to dist/index.js, which does not exist; orphan file user-routes-new.js; ESLint 8 (unsupported), Husky 8 (current is 9), Commander 11 (current is 15), Inquirer 9 (current is 14); engines: >=18, but Node 18 and 20 are already out of support. | Technical debt and outdated configuration passed on to users. |
| Strength | npm audit of the CLI itself: 0 vulnerabilities; ESM and TypeScript code; small create logic (~100 lines). | The rewrite is cheap. |

## 3. Decision

Adopt five principles that apply to every future change and carry out decisions D1 to D9.

### Principles

- Zero runtime dependencies. Any exception requires its own ADR with the justification, size and maintenance history of the package.
- Secure by default. Nothing destructive, no fixed secret, no script run without opt-in.
- Non-destructive and predictable. The same command with the same inputs produces the same result; --dry-run shows what will happen.
- Templates as living data. Templates are tested and audited in CI as if they were products.
- Verifiable supply chain. Every published version can be traced to a commit and a CI build.

### D1 — Replace every dependency with native Node APIs

Require node >= 22 (LTS) and replace:

| Today | Native replacement |
| --- | --- |
| commander | util.parseArgs (node:util) |
| chalk | util.styleText, honoring NO_COLOR and non-TTY output |
| figlet | Static, pre-rendered ASCII banner (the createSimpleBanner function already exists) |
| fs-extra | fs/promises: cp, mkdir, readFile, writeFile, rename |
| inquirer | readline/promises for text, confirmation and numbered choice |
| ora | Simple step messages or a small spinner of our own |

If a richer UX is needed in the future (arrow-key selection, multi-select), evaluate a single small dependency without transitive dependencies, through an ADR.

### D2 — Protections in the create command

- Validate the name with npm's package name rules (lowercase, up to 214 characters, no /, \, .. or absolute path) and make sure the resolved directory stays inside the current directory.
- Refuse a non-empty directory (ignoring .git) unless the user passes --force; with ., list the conflicting files before any write.
- Generate the project in a temporary directory and move it at the end, so an error never leaves a half-written project.
- Copy without following symlinks and make sure in CI that templates contain no symlinks.
- npm install and git init only with explicit opt-in (--install, --git), run with spawn and no shell.

### D3 — Safe and lean templates

- Remove the package-lock.json files from the templates; the lock is created by the user's first npm install with current versions.
- Keep template versions up to date with Dependabot/Renovate and fail CI if the generated project has a high or critical vulnerability.
- Generate a random JWT_SECRET and database password with crypto.randomBytes in the local .env (ignored by git); .env.example keeps only placeholders.
- Publish Postgres on 127.0.0.1:5432 in docker-compose.
- Update tools: ESLint 9 (flat config), Husky 9, engines: >=22; evaluate Express 5.
- Reduce the templates' devDependencies with native features: node --watch instead of nodemon, node --env-file instead of dotenv; evaluate node:test and Node's native type stripping for TypeScript.
- Remove orphan files (user-routes-new.js).

### D4 — Lean published package

- Templates in a single place, resolved from the package root (not copied into dist).
- A files field without compiled tests or unnecessary .d.ts files; fix or remove main; take prepare out of the published package.
- Size budget in CI: fail if npm pack --dry-run exceeds 300 KB unpacked.

### D5 — Supply chain

- Publish only from GitHub Actions with Trusted Publishing (OIDC) and --provenance; mandatory 2FA on the account and no long-lived token.
- CI with npm ci, lint, tests, npm audit, npm audit signatures; actions pinned by SHA; OpenSSF Scorecard.
- SECURITY.md with a reporting channel and a supported versions policy.

### D6 — Functional evolution

General rule: prioritize commands that help in the daily work of people who already created the project, instead of multiplying variations of create. Every new option must fit in the CI test matrix (D5) and keep principle 1. Every command that writes files accepts --dry-run, does not overwrite without --force and respects CI mode (--yes, --json).

#### New commands (high priority)

- qn generate <type> <name> (shortcut qn g): generates the files of a feature already in the right layers. qn g crud product creates the entity, use case, repository interface and implementation, controller, route and test, all wired together. Types: crud, entity, usecase, repository, controller. Options: --only <type>, --no-test, --dry-run. It is what keeps clean architecture in the project after create.
- qn check: validates the dependency rule of clean architecture. Reads the imports (without dependencies, only with fs and simple import/require analysis) and fails if, for example, domain imports infrastructure, Express or the ORM. Readable output and --json; non-zero exit code for use in CI and pre-commit. It sets the library apart from other scaffolders.
- Instructions for AI agents in the generated project: an AGENTS.md (with a copy in CLAUDE.md) describing the layers, the dependency rule, how to run tests, lint and qn check, and how to use qn generate. This way assistants such as Copilot and Claude Code respect the architecture. Also available in existing projects through qn add agents.
- qn add <resource>: idempotently applies a tool to an existing project, with --dry-run showing the diff. It realizes the vision of "commands that configure tools". Recipes:
- Already planned: docker, eslint, husky (with commitlint), swagger, github-actions, tests.
- New: auth (JWT with the secret read from .env), healthcheck (health and readiness routes), ci (GitHub Actions with lint, tests, qn check and npm audit), multi-stage docker running without root, graceful-shutdown, rate-limit and agents.
- qn doctor: checks the Node version, .env, Docker and the project's vulnerabilities, and runs qn check.

#### New commands (later)

- quicknode.json in the generated project: records the choices made in create (database, package manager, template version, folders of each layer). qn add, qn generate, qn check and qn upgrade read this file to know how the project is organized. Enables presets: qn create --preset api-minima or a local JSON preset, validated before use.
- qn upgrade: applies the improvements of a new template version to an existing project. Uses quicknode.json and the hash of the generated files to tell apart what the user changed; unchanged files are updated, changed files get a diff for manual review. Always with --dry-run and never overwrites without confirmation. It is the most complex item on the list.
- qn env: compares .env with .env.example, lists missing or extra variables and generates secrets with crypto.randomBytes (qn env --generate-secrets). Never prints secret values.

#### Configuration options for create

| Option | Values | When |
| --- | --- | --- |
| --db | postgres, sqlite, none | With modular templates (minimal base + add-ons) |
| --pm | npm, pnpm, yarn | Cheap to maintain |
| --test | jest, node | Cheap to maintain; node uses the native node:test |
| --http | express, fastify | Only with real demand; doubles the test matrix |
| --orm | typeorm, prisma, none | Only with real demand; add one axis at a time |

#### General behavior

- CI mode: --yes (no prompts), --json output, no banner when not a TTY. Banner and donation link only in --help or on the first run.
- No telemetry.
- Out of scope: front-end templates, support for many databases and monorepos. They pull in dependencies and turn the library into another product.

### D7 — Documentation and user interface, with the identity of the personal site

Developers need a clear place to learn how to use the library and the generated project. This interface lives outside the npm package, so it does not break principles 1 and 2, and follows the same visual identity and technical rules as the personal professional site (daksonc.github.io), so the project is recognized as part of the same portfolio.

#### Where it lives and how it is built

- A static site in docs/ in the QuickNode repository, published by GitHub Pages. Since the personal site is already daksonc.github.io, the documentation naturally lives at daksonc.github.io/QuickNode/, on the same domain.
- Same architecture as the personal site: plain HTML, CSS and JavaScript, no framework, no mandatory build step and no third-party resources (no CDN, Google Fonts or analytics). This also honors principle 1 in the documentation.
- The command reference is generated by a Node script of our own, without dependencies, from the same definition used by parseArgs, so the documentation never diverges from the CLI. The generated HTML is committed.
- Same budget as the site: every page under 100 KB (font not included).

#### Visual identity (tokens of the personal site)

| Element | Dark theme (default) | Light theme ("dot-matrix printout") |
| --- | --- | --- |
| Background | #000 | #f4f1e6 |
| Text | #33ff66 (terminal green) | #1a1a1a |
| Secondary text | #22b24a | #5c5c5c |
| Highlights and links | #ffc94d (amber) | #7a4a00 |
| Font | VT323 (OFL license), served locally; fallback ui-monospace, Consolas, Courier New | Same |

- DOS terminal look: a prompt in the header (e.g. C:\QUICKNODE>), buttons and selectors in brackets ([MENU], [EN], [PT]), section titles with a dashed line, lists with the > marker and code blocks as terminal output.
- WCAG 2.2 AA accessibility, as on the site: minimum contrast of 4.5:1 in both themes, visible focus with green/black inversion, correct lang and content readable at 320 px.
- CRT effects (glow and scanlines) on by default ([FX: ON]), with [FX: OFF] to turn them off (the choice is remembered); only in the dark theme, and animations stop with prefers-reduced-motion.
- Bilingual EN/PT, with the same page structure and language selector as the site; light/dark theme saved before the first paint, without a "flash".
- An optional command line on the page, as on the site, simulating qn --help, qn create, qn add and qn ui so developers can try it before installing. It is progressive enhancement: the page works fully without JavaScript.
- Consistency in the terminal: the CLI itself uses the same color logic through util.styleText (green for success, amber for highlights and links) and the ASCII banner follows the same style.
- The tokens are copied to docs/assets/css/ with a comment pointing to their origin, instead of imported from the site's repository, so both projects publish independently.

#### Minimum content

- Getting started; reference of every command and flag; structure of the generated project and the role of each clean architecture layer; how to create a new entity and use case; qn add recipes; frequently asked questions; the published ADRs.
- Offline help in the terminal: qn help <command> and qn <command> --help, always with examples.
- qn ui [topic] (alias: qn docs [topic]): opens the user's browser on the documentation page. Rules:
- Fixed URL: base [https://daksonc.github.io/QuickNode/;](https://daksonc.github.io/QuickNode/;) the topic only picks an entry from a closed list (e.g. start, create, add). No text typed by the user goes into the URL, which prevents redirection to another site.
- Native opening, without a shell: spawn with arguments as a list, using the system program: open (macOS), explorer.exe (Windows; never cmd /c start, which interprets &) and xdg-open (Linux). Detached process and unref, so the CLI exits right away.
- The link is always printed in the terminal. In CI, SSH, a container or non-interactive output, the command only prints the link and does not try to open anything; the --print option forces this behavior.
- Silent failure: if there is no program to open links, the printed link is enough and the command ends successfully.
- Zero dependencies: no packages such as open.
- The generated project gets a README with the folder map and links to the guide.

Out of scope: a web server or UI embedded in the CLI. qn ui only opens the published documentation; it never starts a local server, opens a port or adds dependencies to the package. A local UI would only be reconsidered, through its own ADR, if real demand appears (for example, a visual project creation wizard).

### D8 — SEO and discovery of the library

Goal: make the library findable by people searching for scaffolding and clean architecture solutions in Node.js, without telemetry and without third-party resources.

#### On the documentation site

- Metadata per page: a unique <title> and meta description, link rel="canonical" and hreflang EN/PT (with x-default), following the personal site's pattern.
- Sharing: Open Graph and Twitter Card with a preview image (1200×630) in the D7 terminal look.
- Structured data (JSON-LD): SoftwareApplication on the home page (name, description, license, npm and repository links) and BreadcrumbList on inner pages.
- Sitemap and robots: its own sitemap.xml at daksonc.github.io/QuickNode/sitemap.xml. Since robots.txt only applies at the domain root, which belongs to the personal site's repository, QuickNode's sitemap is referenced in the personal site's robots.txt. Verifying the daksonc.github.io domain in Google Search Console covers both.
- Search-oriented content: pages and tutorials, in EN and PT, for intents such as "Node.js clean architecture boilerplate", "Express + TypeScript with clean architecture", "how to create a use case" and "how to validate the dependency rule"; a public changelog per version.
- Crawlability: all content is in the HTML; the terminal simulator and the effects are only progressive enhancement. Clean, stable URLs per topic (the same ones used by qn ui).
- Performance: 100 KB limit per page, font preload and font-display: swap; Lighthouse target > 95 in SEO, performance and accessibility.
- Optional: an llms.txt with a summary of the documentation, for AI-powered search engines and assistants.

#### SEO for AI search engines

Besides traditional search engines, the documentation should be easy for AI search engines and assistants (ChatGPT, Claude, Perplexity, Google's AI answers) to read, understand and cite. This complements the llms.txt, the .md pages and the positioning defined in D9.

- AI robots in robots.txt: explicitly allow AI crawlers (e.g. GPTBot, ClaudeBot, PerplexityBot and Google-Extended) so the documentation can be read and cited. Since robots.txt sits at the domain root, in the personal site's repository, the rule applies to both sites and is recorded there as well.
- Answer-shaped content: every page starts with a sentence that directly answers its main question (e.g. "To create a Node.js API with clean architecture, run npx @10565/quicknode-cli create my-api"), uses question-shaped headings and numbered steps, to make snippets easy to extract.
- Visible dates and versions: every page shows "updated on" and the version it applies to (e.g. "valid for v2.x"), also in JSON-LD (dateModified, softwareVersion), to signal that the source is current.
- Consistent facts on every channel: name, install command, current version and positioning sentence identical on npm, GitHub, the documentation and external articles. Contradictory information across sources leads models to make mistakes or stop recommending the library.
- An honest comparison page: when to use QuickNode, Nest CLI or a manual template, with objective criteria, since comparative questions are frequent in AI assistants.
- Known limit: optimization for AI search engines is still recent and changes fast; these items increase the chance of being cited but do not guarantee it, and there is no tool equivalent to Search Console to measure it. Tracking is done with periodic queries to AI assistants (e.g. "how to create a Node.js API with clean architecture"), recording whether the library shows up and whether the cited data is correct.

#### On npm and GitHub

- package.json: an objective description; broader keywords (scaffold, generator, boilerplate, clean-architecture, express, typescript-template, nodejs); homepage pointing to the documentation; correct repository and bugs.
- npm quality signals: provenance, tests, frequent releases and zero dependencies (D1 to D5) also improve the position in npm search.
- GitHub: description and topics on the repository, the "Website" field with the documentation link, a social preview image, releases with notes and a README that opens with a GIF of qn create and the install command.
- npm create quicknode: the create-quicknode alias (section 4) is also a discovery channel.
- Credit in generated projects: a "Generated with QuickNode" line with a link in the project's README, removable with --no-credits. Never in code, HTTP headers or API responses.

#### Outside the code

- Technical outreach: the TCC (thesis) article, when published, citing the library as an academic reference; articles on dev.to and LinkedIn showing qn check and qn generate.

Out of scope: analytics, tracking pixels or any collection of visitor data, consistent with the "no telemetry" and "no third-party resources" rules.

### D9 — Experience for AI agents

LLMs and coding agents (Claude Code, Copilot, Cursor and similar) now suggest, install and operate the library on behalf of developers. The agent's experience is treated as a first-class user experience: the agent needs to discover what the library does, run it without hanging, understand errors and produce code that respects the architecture, always with the person in control of actions that change files.

#### A CLI agents can operate

- Never block: every interactive prompt has an equivalent flag. Without a TTY (agent, CI, pipe), qn never asks: it uses the declared defaults or fails immediately saying which flag is missing.
- Self-description: qn schema (and qn --help --json) returns the full specification of commands, flags, accepted values and defaults in JSON, generated from the same definition used by parseArgs and by the documentation (D7). The agent discovers what exists instead of inventing flags.
- Actionable errors: every error has a stable code, a short message and a suggested fix, also in --json (e.g. {"code":"E_DIR_NOT_EMPTY","message":"…","fix":"qn create my-api --force"}). Codes and exit codes are documented.
- Plan before acting: --dry-run --json returns the list of files to create, change or remove, so the agent can show it to the person before applying.
- Stable output: the JSON format is versioned; incompatible changes only in a major version.

#### MCP server

- Expose create, generate, add, check, doctor and schema as MCP (Model Context Protocol) tools, so assistants call the library in a structured way instead of assembling shell commands.
- Distributed as a separate package (@10565/quicknode-mcp) or implemented with minimal JSON-RPC over stdio, without an SDK, to keep principle 1 in the main package.
- Security: acts only inside the project directory; no network access; dry-run by default; writes only with an explicit confirmation parameter; never runs arbitrary commands.

#### Documentation readable by LLMs

- llms.txt (index) and llms-full.txt (full content) at the documentation root; every page is also available in Markdown at the same URL with .md.
- A "For AI agents" page with exact, non-interactive, version-pinned commands (e.g. npx @10565/quicknode-cli@2 create my-api --typescript --db postgres --yes), the recommended flow and the error codes.
- A "When to use and when not to use" page, with clear criteria, so models recommend the library only in the right contexts.
- A single positioning repeated on npm, in the README, on GitHub and in the documentation: "Zero-dependency CLI to create Node.js APIs with clean architecture".

#### Protection against hallucination and name confusion

- "QuickNode" is also the name of a blockchain infrastructure provider. README and documentation carry an explicit notice ("not to be confused with…") and the full scoped package name in every example.
- Reserve similar names on npm (create-quicknode and unscoped variations) to prevent typosquatting of packages LLMs might suggest by mistake.
- Safe installation even without human review: no lifecycle scripts (preinstall, postinstall), no download during generation and provenance to verify the origin (D5).
- Templates and documentation never contain instructions aimed at agents outside the project's scope, to leave no room for prompt injection.

#### A generated project ready for AI

- AGENTS.md (D6) tells the agent to prefer qn generate over writing structure by hand, to run qn check and the tests after every change and to record decisions in docs/adr/.
- qn check and tests act as guard rails: immediate, deterministic feedback for the agent to fix its own code.
- A docs/adr/ folder with an ADR template in the generated project, so architecture decisions are recorded and respected by people and agents.

#### Continuous evaluation with agents

- A battery of real tasks run periodically by agents (e.g. "create an API with Postgres and a product CRUD", "add JWT authentication"), measuring the success rate without human intervention, invented flags and violations reported by qn check.

Out of scope: calling LLMs from the CLI, embedding API keys or sending user code to external services. The library becomes easy for agents to use, but stays offline and without telemetry.

## 4. Alternatives considered

| Alternative | Decision | Reason |
| --- | --- | --- |
| Keep the dependencies and only update versions | Rejected | Keeps the 56 packages and the attack surface. |
| Switch to smaller libraries (picocolors, cac, @clack/prompts) | Plan B | Reduces the weight but still depends on third parties; remains a possible exception through an ADR. |
| Download templates from a remote repository (degit/giget style) | Rejected | Requires the network, opens a supply chain point at generation time and loses reproducibility and offline use. |
| Also publish as create-quicknode (npm create quicknode) | To evaluate | Improves discovery; depends on the name being available on npm. |
| MCP server inside the main package, using the official SDK | Rejected | Would add dependencies to the package every user installs; a separate package or minimal JSON-RPC keeps principle 1. |
| Integrate an LLM into the CLI itself (e.g. generate code from a prompt) | Rejected | Requires API keys, the network and sending code to third parties; agents already do this better using the library as a tool. |
| Documentation generator (VitePress, Astro Starlight) with a custom theme | Rejected | Brings dozens of dependencies and a build step, and would mean fighting the default theme to reproduce the terminal look; the personal site already proves that plain HTML/CSS does the job. |

## 5. Consequences

### Positive

- Almost instant installation through npx, with a single package.
- Generated projects without known vulnerabilities and without fixed secrets.
- No risk of deleting the user's files.
- Verifiable releases and documentation with the same identity as the personal site, which increases confidence for adoption and strengthens the portfolio.

### Negative and risks

- Requiring Node 22+ is a compatibility break: the change ships as v2.0.0 (semver major), with a migration note.
- Native prompts are less sophisticated than inquirer's.
- Keeping templates up to date becomes continuous work, mitigated by automation (Dependabot + CI that generates and tests the projects).
- The JSON format and the error codes become a public contract: changing them breaks agents and integrations, so they require careful versioning.
- Copied visual tokens may drift from the personal site over time; mitigate with a CI check that compares the CSS variables of both repositories.
